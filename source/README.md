# 適ケアくん

適切なケアマネジメント手法・活用ツール（β / v0.3）

ケアマネジャーが事例の原文を整理し、次に「誰に、何を、なぜ確認するか」を検討するためのブラウザアプリです。React / TypeScript / Vite。静的配信のみで動き、有料API・APIキー・バックエンドは不要です。

> **独立した試作版です。日本総合研究所・厚生労働省の公式アプリではありません。** 令和7年度本文の基本ケア44支援・疾患別163支援を番号・名称・階層・参照ページ付きで収録しています。照合ルールと質問は独自作成です。従来の独自44視点も別に表示し、公式44支援と同一視しません。専門職による実用精度の独立評価は未実施です。

## できること

- 自由記述から、原文位置を保持した記載単位のObservationを抽出。入力を真実と認定するのではなく「入力に報告された内容」として扱います。
- 令和5年10月16日改正の課題分析標準項目23項目へ複数分類し、そのままコピー。生活歴・口語・略語・見出しを手がかりに分類します。分類先は複数選択で修正でき、未分類もその場で整理できます。
- 公式207支援を原文と照合。領域・期・番号・名称で絞り、各支援の実施内容を原典で確認できます。期や支援の必要性は自動確定しません。
- 事例レビューモードは独自44視点から上位5件の確認候補を別表示。短期・継続・低優先・未記載を区別します。
- 根拠原文 → 事例の捉え方（仮説）→ 確認視点 → 判定理由 → 確認先候補・質問をトレース表示。
- 否定記載、過去の記載、推量を考慮。未記載だけで全項目を「不足」「優先」にしません。
- 研修モードで自分の着目点を選んでから、結果との違いを比較。正解・不正解とは表示しません。
- 完全架空の10サンプル。明示操作による事例JSONの保存・再読込。
- 「適ケアを調べる」：基本ケア・疾患別・23項目を体系とキーワードで検索。独自の確認質問と公式冊子の該当章を表示。
- 「資料の更新」：厚労省・日本総研の掲載リンクと採用PDFの変更を確認。取得失敗・古い確認結果も区別。
- ライト／ダークモード、スマホ・タブレット対応。表示テーマと、希望時に公式資料PDFをブラウザに保存。
- 任意のローカルAI、モデル選択、進捗、中止、キャッシュ削除、Knowledge Pack読込。

## 動かす

Node.js 22以上を用意し、このフォルダで実行します。

```sh
npm ci
npm run dev
```

表示されたローカルURLを開き、サンプルを選んで「この事例を分析する」を押してください。軽量モードはモデル取得なしで使えます。

```sh
npm run typecheck
npm run lint
npm test
npm run build
npx playwright install chromium
npm run test:e2e
```

`dist/`が静的公開用ファイルです。`file://`でHTMLを直接開かず、開発サーバーかHTTPSの静的ホスティングを使用してください。

## 端末内処理と通信境界

事例本文はReactのメモリとWorker内だけに置きます。localStorage / IndexedDB / Cookieへの事例自動保存、アクセス解析、遠隔エラー送信、外部推論APIは実装していません。更新・タブ終了で事例は消えます。保存JSONには原文と根拠を含む結果が入ります。再読込では本文から再分析し、原文位置・本文が一致した手動分類だけ復元します。その他の保存結果は信用しません。表示テーマはlocalStorageに保存します。公式資料PDFは利用者が読み込んで保存を選択した場合に限りIndexedDBへ保存し、資料画面で削除できます。事例データはここへ保存しません。

- **軽量モード**：辞書、関連グラフ、決定的ルール。配信元以外への通信は不要です。
- **AIモード**：設定で明示的に準備した後、WebLLMを専用Workerで実行します。初回はHugging Face / GitHub等からモデルを取得します。推論本文をその配布先へ送る処理はありません。
- 埋め込みはTransformers.jsの多言語MiniLMをWASMで端末内実行。モデルは初回分析時に取得し、取得失敗時は辞書・関連グラフへ復帰します。
- アプリ内の更新確認は同じ配信元の公開JSONを取得します。公式資料リンクは別タブで開きます。AI処理の外部通信はモデルや実行資産の取得に限定。CSPで接続先を絞っています。モデル配布側には通常のダウンロード通信のIP等が伝わります。CSPは入力送信防止の唯一の保証ではなく、実装・依存関係の監査と合わせて扱います。
- ブラウザキャッシュにはモデル資産を保存します。サイト自体のオフライン起動を保証するService Workerは未実装です。
- コピーした内容はOSのクリップボードに残るため、組織の取扱規程に従ってください。

## ローカルAI

WebGPUが利用できるブラウザで、設定 → 利用可能なモデルを表示 → AIのタイプ（基本／高機能）→ モデル準備の順に操作します。モデル一覧はインストール済みWebLLMの`prebuiltAppConfig`から構築し、用途に合わないCoder/Mathモデルは除外します。個別のモデルID・量子化形式を選びたい場合は詳細設定（既定では折りたたみ）から選択できます。

- 基本：0.5B〜1.5B程度。ダウンロードは概ね数百MB〜1GB台。**まずはこちら。**
- 高機能：7B程度。メモリ16GB以上を目安。動作保証ではありません。「次に聞いてみたいこと」の自由生成を使いたい場合のみ必要です。

表示ダウンロード量はパラメータ数に基づく概算で、正確な配布サイズ・必要VRAMとは異なります。埋め込みモデルも約120MB必要です。端末・ブラウザ・WebGPUアダプター・モデルによって準備や推論が失敗することがあります。

`eval/cases`の10架空事例による開発環境の比較（`scripts/eval-candidate-selection.mjs`、結果は`eval/candidate-selection-report.json`）では、候補選択で測定した3指標（Critical Recall・Useful Precision・Priority Hit Rate）は基本（0.5B）と高機能（7B）で同じ値でした。ただしこれは集計指標が一致しただけであり、個々の候補のスコアや優先度判定まで完全に同一だったことは確認していません。候補選択はルールベース・辞書照合・意味検索が中心のため、モデルサイズによる精度差はこの3指標では確認できませんでした。実機検証では、高機能（7B）による「次に聞いてみたいこと」の自由生成は、他のアプリやブラウザタブが多数動作した状態で5〜8分程度かかることがありました。以上から、通常利用は基本を既定とし、高機能は自由生成機能を使いたい・高性能な端末を持つ利用者向けの追加選択肢として案内しています。

5観点（本人意向／健康／生活機能／家族・環境／連携）で独立に候補を検討し、根拠の関連・変化・生活への影響と決定的ルールで統合します。同一モデルの繰り返しであり、専門家5人の合意や臨床的な確信度ではありません。

自由生成した文章を事実として採用しないため、候補選択の段階ではLLMの出力を提示した項目IDと原文IDの選択に制限します。JSON Schema拘束、Zod検証、根拠ID検証、簡易構文修復、再試行を行い、失敗時はルール結果を保持します。事実抽出は原文または独自の定型文です。全パイプラインをLLMで自由生成する方式ではありません。

Qwen2.5-7B-Instruct（高機能）のみ、候補選択の後に「次に聞いてみたいこと」を自由生成します。確認視点・質問相手・原文・公式番号はアプリが固定し、LLMは質問（question）・理由（reason）・次の検討（nextStep）の3文だけを生成します。生成文はプレースホルダー検出・質問形式・不適切表現の形式検査のみを行い、意味の正しさや臨床的妥当性は保証しません。検査に落ちた場合は1回だけ再生成し、それでも通らなければ表示せず件数を通知します。基本のモデルはこの自由生成に使わず、候補選択のみに利用します。

## 評価と限界

`eval/cases`に10件の架空事例、`eval/expected`に複数の有用な視点と禁止する事実補完の例を置いています。`npm run eval`で`eval/report.json`を再生成します。

- Critical Recall：期待した概念が確認候補に含まれる割合。
- Useful Precision：上位5件のうち、事前に用意した有用項目集合に属する割合。
- Priority Hit Rate：上位5件に少なくとも1つ有用項目がある事例割合。
- Assessment23 Accuracy：事例ごとの分類集合と期待集合のJaccard一致率。
- Unsupported Claim Rate：事実欄が原文を逸脱した割合。原文保持方式の回帰検証に限り、仮説の妥当性や質問の適切性を測りません。
- Trace Coverage：提示候補の根拠IDが原文に解決する割合。

これらは少数の開発用データに対する回帰指標です。実務性能・見落とし率・臨床精度を示すものではなく、同じ作者の期待データに偏ります。実事例を使う前に、匿名化した独立データと専門職の検討で評価してください。

日本語の否定・主体・時系列・推量の解析は完全ではありません。一文内の複数主体や二重否定などは原文で確認してください。「確からしさ」「確認順の参考値」は未較正の目安で、医療診断・危険度スコアではありません。確認質問はすでに記録に答えがある場合もあり、追加確認候補として表示します。

## GitHub Pagesで公開

1. 自分のGitHubで新規リポジトリを作成します（例：`tekicare-app`）。利用者の事例JSONは登録しないでください。
2. `npm run typecheck && npm run lint && npx vitest run && npm run build` が通ることを確認します。
3. `node scripts/prepare-static-release.mjs` を実行し、`../tekicare-static-release/` に公開候補（ビルド済み静的ファイル＋`source/`にソース一式）を生成します。
4. 生成された内容をリポジトリの`main`ブランチ直下にコミット・pushします。GitHub Actionsでのビルドやgh-pagesブランチは使いません。
5. リポジトリの **Settings → Pages → Build and deployment → Source → Deploy from a branch → main / (root)** を選びます。

Viteの`base: './'`で任意のリポジトリ名のサブパスに対応します。ルーターを使わない単一ページのため、SPAリライト設定は不要です。公開前のCIは型検査・lint・単体／統合テスト・ブラウザテストをローカルで実行して確認します（自動デプロイの仕組みは組み込んでいません）。

## 公式資料の更新確認

自動実行の仕組みは組み込んでいません。サイト運営者（kat-t00）が`npm run check:sources`を手動で実行し、厚労省の通知一覧2ページ、日本総研の資料一覧1ページ、採用PDF2件を取得して、関連リンク・PDFのSHA-256を基準と比較します。変更・取得失敗を公開JSONに記録し、画面で表示します。画面には確認日時を表示し、3日超の結果を古い情報として扱います。

「更新情報を読み直す」は配信済みの結果を取得する操作です。公式サイトをその場で巡回するものではありません。監視対象外の変更まで網羅する保証はなく、ルールや採用版を自動で書き換えることもありません。変更を人が確認してから採用版を更新してください。

```sh
npm run check:sources
# 公式資料の変更内容を確認し、採用判断とデータ修正を終えた後のみ：
node scripts/check-sources.mjs --accept-baseline
```

設定は `knowledge/public/source-monitor.json`、比較基準は `source-baseline.json`、画面用結果は `public/updates.json`。基準の変更はソースとともにコミットします。監視処理が取得するのは公式資料だけで、事例本文は扱いません。ローカル利用時も上記コマンドで結果を更新できます。GitHubへの公開はまだ実行していません。

## 実機レビュー対応・第1組

原文の改行・追記・再分析でも、手修正した記録文を保持します。原文変更後は照合を促す表示が出ます。再分析前の保存も編集文を含みます。別のサンプル・保存事例へ切り替える場合や消去する場合は、編集文があれば確認します。

「原文から作り直す」は「原文ベースの文と比較」に変更。未変更なら無効、編集済みなら現在の文と置き換え案を表示し、明示的な置き換え操作後も取り消せます。置き換え後に再び手入力した場合は古い取り消しで新しい入力を消さないため、取り消しボタンを解除します。

23項目整理画面の「事例ファイルを保存」で再開用JSONを取得できます。「この整理先を反映」は画面内の分類変更でありファイル保存ではありません。ヘッダーの使い方と項目移動の一覧を追加しました。

分類・質問に関する3件もユーザーが示した方針で修正。在宅希望は23項目の07と適ケアの意思決定過程へ、過去の転倒は現在の否定を保持してリスク予測へ関連付けます。転倒だけから意思疎通を上位候補にしません。公開していません。
